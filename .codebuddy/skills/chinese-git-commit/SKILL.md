# 中文 Git 提交规范

## 目标

生成便于维护者和 AI 理解的中文 Git 提交信息。确保 message 准确覆盖实际改动、解释变更动机，并避免把互不相关的内容混入同一提交。

## 工作流程

1. 检查 `git status --short`、已暂存文件清单和 `git diff --cached`。
2. 识别实际行为变化、文档变化、配置变化、数据迁移及兼容性影响，不仅依据文件名概括。
3. 判断所有改动是否服务于同一目标。对相互独立的主题，优先拆分提交；无法拆分时，在正文中分别解释每个主题。
4. 按本规范编写简体中文标题和正文。
5. 提交前逐项核对 message 与 staged diff；提交后使用 `git show --stat --format=fuller HEAD` 复核。
6. 仅在用户明确要求提交时执行 `git commit`；仅在用户明确要求修正上一提交时执行 `git commit --amend`。

## 语言要求

- 标题和正文统一使用简体中文，不使用英文句子。
- 保留无法合理翻译或翻译后会失真的技术标识，例如函数名、文件名、协议名、依赖名和 `SQLite`、`API`、`Git`。
- 使用准确、直接、可验证的表述，避免“优化一下”“调整代码”“修复问题”等缺乏信息量的描述。

## Message 结构

采用以下结构：

```text
<类型>(可选范围): <中文动作摘要>

<说明做了什么，以及关键实现或影响。>

<说明为什么这样做，包括背景、风险、约束或取舍。>
```

标题要求：

- 使用动宾结构，概括提交的核心结果。
- 建议控制在 50 个汉字以内。
- 不以句号结尾。
- 类型按主要改动选择：`功能`、`修复`、`文档`、`重构`、`测试`、`构建`、`集成`、`维护`、`性能`、`回退`。
- 同时包含多种改动时，按主要用户价值选择类型，不得用类型掩盖未说明的次要改动。

正文要求：

- 必须同时回答“做了什么”和“为什么这样做”。
- 必要时补充兼容性、迁移方式、边界条件、风险和验证结果。
- 描述行为和意图，不逐行复述 diff。
- 存在破坏性变更时，明确标注影响范围和迁移要求。

## Diff 对照检查

提交前逐项确认：

- message 中每项“做了什么”都能在 diff 中找到证据。
- diff 中每个有意义的变化都被标题或正文覆盖。
- “为什么”与实际改动解决的问题一致，不虚构背景或效果。
- 文档、测试、配置、生成物和删除操作均未遗漏说明。
- 没有把计划中的后续工作写成已经完成。
- 验证结果只写实际执行且通过的检查。

发现不一致时，先修正暂存内容或 message，再提交。不要为了匹配 message 而擅自扩大代码改动。

## 原子提交判断

满足以下任一情况时优先拆分：

- 改动服务于不同业务目标。
- 文档或格式调整与功能修改没有直接关系。
- 一个主题可以独立回滚，而不影响另一个主题。
- 单一标题无法准确概括全部变更。

直接支撑同一目标的代码、测试和文档可以放在同一提交中。

## 示例

```text
修复(账单): 修正跨月抄表时的用量计算

按账期边界读取上期表底，并补充跨年月份和首次抄表测试，避免将前一自然月之外的记录作为起始读数。

原实现只按月份排序，在跨年和补录场景下可能生成错误账单；明确账期边界可以保持历史账单一致，并降低后续数据修复成本。
```

```text
维护: 隔离本地敏感数据并记录系统架构

扩展运行配置、环境变量、凭据、证书和本地数据库的忽略规则，同时新增物业管理架构说明及配套图。

本地文件可能包含密码哈希、账单数据和机器配置，需要阻止其进入版本库；架构文档用于记录模块边界、数据流和迁移约束，方便后续维护者和 AI 延续设计决策。
```

## 输出与执行

- 用户只要求 message 时，仅给出可直接使用的中文提交信息，不执行提交。
- 用户要求提交时，先展示或概括 staged diff 与 message 的对应关系，再执行提交并报告提交哈希。
- 用户要求审查时，先指出不对应、遗漏或不够原子的部分，再给出修订后的完整中文 message。
- 修正已推送提交前，说明需要改写远程历史，并遵守受保护的推送流程。
